Currently, creating a card and assigning it to an epic requires two separate steps (`kanbai_create_card` + `kanbai_set_card_epic`). This feature adds an `epic` parameter directly to the card creation flow.

## Requirements

- Add an optional `epic` field to `kanbai_create_card` (MCP tool) and the `create` CLI command
- If `epic` is provided, assign it atomically during card creation
- If the specified epic does **not exist**, return a clear validation error (do not create the card)
- Error message should indicate the invalid epic name and suggest listing available epics

## Acceptance Criteria

- [ ] `kanbai_create_card` MCP tool accepts an optional `epic` parameter
- [ ] CLI `create` command accepts an `--epic` flag
- [ ] Card is created **and** assigned to the epic in a single operation
- [ ] Passing a non-existent epic name returns an error and does **not** create the card
- [ ] Existing behavior (no epic) is unchanged

---
**Fixed 2026-06-22**
- **Understood:** The `operations.create_card` layer already accepted `epic` and raised `EpicNotFoundError` / `EpicArchivedError` on invalid input. Both the CLI `add` command (via `--epic` flag) and the MCP `create_card` tool already forwarded the `epic` argument. The CLI already caught `ValueError` properly. The MCP tool was the gap — it let the exception propagate raw to FastMCP rather than returning a clean `{"error": "..."}` dict.
- **Encountered:** No structural changes needed — just wrapping the `operations.create_card` call in the MCP tool with a `try/except`.
- **Fixed:** Added `try/except EpicNotFoundError / EpicArchivedError / ValueError` in the MCP `create_card` tool. On `EpicNotFoundError`, returns `{"error": "...", "available_epics": "..."}` listing current epics. Updated docstring to document the `epic` parameter and its validation behaviour. CLI was already correct — no changes needed there.
