## 1. Board-lanes neighbourhood graph dialog ✅

**Status:** Done.

Replaced the cramped radial `open_graph_dialog` (fixed 860×480, all neighbours
in a circle) with a proper board-lanes layout — same engine as
`GraphPage._build_graph_content()` — scoped to the focal card and its 1-hop
neighbours.

**What changed (`ui/graph_page.py`):**
- Cards are placed in their actual **Backlog / In Progress / Review / Done**
  lane so you see their progress at a glance.
- The focal card gets an orange highlight border.
- Cross-epic neighbours appear faded (ghost style) in their own lane, with
  their epic shown.
- Dialog grows up to 1 100 px wide and scrolls both axes for cards with many
  relationships.
- Close button is an icon button (`CLOSE_ROUNDED`), consistent with the card
  dialog.

## 2. Due dates / deadline field ✅

**Motivation:** The most common missing Kanban primitive. Needed for filtering
overdue work, sorting by deadline in the table, and future burndown analytics.

### Data model

Add `due_date: str | None = None` to `board/models.py::Card`.
Format: `YYYY-MM-DD` (date-only ISO string, timezone-agnostic for display).

```python
# board/models.py
due_date: str | None = None
```

`to_frontmatter()` and `from_frontmatter()` include it. SQLite cache adds a
`due_date TEXT` column (migration: `ALTER TABLE cards ADD COLUMN due_date TEXT`).

### operations.py

`create_card` and `update_card` accept `due_date: str | None = None`.

### UI touch-points

| Location | Change |
|---|---|
| `card_dialog` — edit tab | Date picker / text field (YYYY-MM-DD) |
| `card_dialog` — view tab | Show due date chip; red if overdue |
| `board_view` board tile | Tiny calendar chip at the bottom when set; red if overdue |
| `table_page` | New "Due" column (index 10, after Age); sortable; red text when past today |
| `table_page` | New "Due" filter dropdown: Any due / Overdue / This week / No date |

### MCP

`create_card` and `update_card` tools gain an optional `due_date` parameter.

## 3. Global card search (Ctrl+K)

**Motivation:** No way to jump to a card by keyword across all views. Becomes
critical as the board grows beyond ~50 cards.

### Behaviour

- `Ctrl+K` from anywhere in the app opens a floating overlay (drawer-style or
  centred modal).
- Text input searches title + description + tags + assignees in real time using
  the existing SQLite FTS / `LIKE` query in `sqlite_cache.query_cards()`.
- Results list is keyboard-navigable (↑ ↓ Enter).
- Clicking or pressing Enter opens the card dialog.
- `Escape` dismisses.

### Implementation

New helper `ui/search_overlay.py::open_search_overlay(page, open_card_fn)`.
`main.py` registers a `page.on_keyboard_event` handler that calls it on
`Ctrl+K`. No new storage required — queries go directly to the SQLite cache.

## 4. Constraints & validation layer ✅

**Status:** Done.

New module `board/validation.py` enforces all hard limits; called from
`operations.py` before every write.

**Motivation:** AI agents (embedded chat, MCP) can write to cards without human
review. Without limits an agent could produce 300 tags, a 10 000-character
description, 50 relationships, or flood the comments — bloating every markdown
file and degrading UI performance.

All limits are enforced in `operations.py` (the single orchestration layer) so
they apply uniformly to the UI, the chat agent, and external MCP callers.

### Hard limits (raise `ValueError` — rejected silently)

| Field | Limit | Rationale |
|---|---|---|
| `title` | 1–200 chars | Titles drive file names + display; empty or monster strings break layout |
| `description` | ≤ 10 000 chars | Large enough for thorough specs, small enough to keep markdown files sane |
| `tags` | ≤ 10 tags | Filters & chips become unusable beyond this |
| each `tag` | 1–50 chars | Prevents paragraph-length tags |
| `assigned_to` | ≤ 10 names | Reasonable team size |
| each assignee name | 1–100 chars | |
| `links` (relationships) | ≤ 20 per card | Graph view and dialog remain readable |
| `comments` | ≤ 200 per card | History stays git-trackable; old comments can be pruned |
| each comment `text` | 1–4 000 chars | One thorough paragraph / agent report |
| `epic` name | 1–100 chars | |

### Soft warnings (UI only — human is shown a caution but can proceed)

| Situation | Warning |
|---|---|
| Description > 5 000 chars | "Description is long — consider splitting into sub-tasks" |
| Tags > 7 | "Lots of tags — consider using an epic instead" |
| Relationships > 10 | "Many relationships — check for duplicate or redundant links" |

Soft warnings appear as a dismissible banner in the card dialog when the limit
is crossed during a save.

### Implementation

```python
# board/validation.py  (new module)

MAX_TITLE        = 200
MAX_DESCRIPTION  = 10_000
MAX_TAGS         = 10
MAX_TAG_LEN      = 50
MAX_ASSIGNEES    = 10
MAX_LINKS        = 20
MAX_COMMENTS     = 200
MAX_COMMENT_LEN  = 4_000

def validate_card_fields(
    title: str | None = None,
    description: str | None = None,
    tags: list[str] | None = None,
    assigned_to: list[str] | None = None,
    links: list[dict] | None = None,
) -> None:
    """Raise ValueError with a human-readable message on any violation."""
    ...

def validate_comment(text: str, current_count: int) -> None:
    """Raise ValueError if the comment exceeds length or would exceed max count."""
    ...
```

`operations.create_card`, `operations.update_card`, and `operations.add_comment`
call the relevant validators before writing.

### MCP

MCP tool handlers catch `ValueError` from `operations` and return it as a
structured error response (existing pattern). The agent sees a clear message
like `"tags: maximum 10 tags allowed (got 14)"` and can self-correct.

## 5. Comments thread UI

**Motivation:** `Card.comments` is already stored; there is no UI to read or
write it. Comments are the canonical decision log for a card and the
agent-to-human communication channel.

### Comment schema (existing)

```python
{
  "id":         "<uuid>",
  "author":     "user" | "kanbai_bot" | "mcp:<agent_name>",
  "text":       "...",
  "created_at": "2026-06-11T14:32:00Z"
}
```

The `author` field is new — current comments default to `"user"` on read.
`operations.add_comment` gains an `author: str = "user"` parameter.

### Visual identity

| Author pattern | Avatar | Accent colour | Display name |
|---|---|---|---|
| `"user"` | Initials bubble (`avatar_color()`) | Per-user colour | From settings (fallback "You") |
| `"kanbai_bot"` | `SMART_TOY_OUTLINED` icon | Teal (`#2EA0A0`) | "Kanbai" |
| `"mcp:<name>"` | `ELECTRICAL_SERVICES` icon | Purple (`#8B5CF6`) | `<name>` + "via MCP" badge |

### UI placement

Comments live in the **view tab** of the card dialog:
- Scrollable thread of comment bubbles, newest at the bottom.
- Each bubble: avatar left, author + relative timestamp top-right, text body.
- Text input + **Post** button pinned at the bottom of the panel.
- The edit tab stays focused on the card's spec (title, description, etc.) —
  comments are not editable there.

### MCP

New write-tier tool `add_comment(card_id, text, author)`. The `author` field
must start with `"mcp:"` when called via MCP (server enforces this).

## 6. Attachments UI

**Motivation:** `Card.attachments: list[str]` exists on the model and is
persisted to frontmatter, but there is no UI to add or view attachments.

### What attachments are

File paths (absolute or relative to `board_data/assets/`) stored as strings.
No binary content is embedded in the markdown file.

### UI

In the card dialog **edit tab**:
- Attachment list: each entry is a chip with the filename and a remove button.
- "Add file" button opens a native file picker (`ft.FilePicker`); selected path
  is copied into `board_data/assets/` and the relative path stored.

In the **view tab**:
- Chips are clickable — opens the file with `page.launch_url()` (works for
  images, PDFs, etc.) or shows path in a tooltip for non-launchable types.

## 7. Git sync / dirty-state indicator

**Motivation:** Cards are git-trackable markdown files, but there is no signal
that unsaved (uncommitted) changes exist, and no way to commit from the UI.

### Dirty-state indicator

A small dot or badge in the app header (next to "Vault ready") shows when
`git status --porcelain board_data/` returns any output. Checked:
- On app start.
- After any `operations` write (debounced, 2 s).

### Commit action

A "Commit" button (or context menu option) in the header/toolbar:
1. Runs `git add board_data/`.
2. Opens a single-line input for the commit message (default: `"kanbai: <n>
   change(s) <timestamp>"`).
3. Runs `git commit -m "<message>"`.
4. Clears the dirty indicator.

### Implementation

New `board/git_sync.py`:
```python
def is_dirty() -> bool: ...
def commit(message: str) -> None: ...
```

Uses `subprocess.run` with `check=True`. Gracefully no-ops when the
`board_data/` directory is not inside a git repository (e.g. first-time setup).

## 8. Blocker violation indicator

**Motivation:** A card marked `blocked_by` another should not advance further
on the board than the card it is waiting on. Hard enforcement is intentionally
avoided (human override is always valid; MCP agents have legitimate reasons to
pre-stage cards). A visible warning surfaces the inconsistency without blocking
the workflow.

### Rule

```
COLUMN_RANK = {backlog: 0, in_progress: 1, review: 2, done: 3}

violation: rank(blocked_card) > rank(blocker_card)
```

### Surfaces

| Location | Indicator |
|---|---|
| **Board tile** | Small amber warning icon (`WARNING_AMBER_ROUNDED`) bottom-right of the card chip, with tooltip listing the blocker numbers |
| **Card dialog — view tab** | Amber banner: "This card is ahead of its blocker(s): #X (Backlog), #Y (In Progress)" |
| **Card dialog — edit tab** | Same banner shown when saving a column change that introduces a violation |

### Implementation

`board/operations.py` gains a pure helper:

```python
def blocker_violations(card: Card) -> list[dict]:
    """Return rows for each blocker that ranks behind this card's column."""
    ...
```

Called lazily in the UI — no new storage, no writes, no enforcement.
